# AGENTS.md

keel is an extension for omp (oh-my-pi) and Pi: algorithmic compaction (no LLM call), pinned notes, and `keel_recall` over the raw session history and the project's other sessions. A fork of pi-vcc. Each host has its own entry written against that host's own code, which is its API (`index.ts` for omp, `pi.ts` for Pi), over one shared core. User-facing docs are in `README.md`; keep it short and put contributor notes here.

## Checks

```sh
bun install --frozen-lockfile --ignore-scripts
bun run setup:omp
bun run setup:pi
bun run typecheck
bun run test
```

omp is not a dependency: it releases often, and a pinned copy would test a version users have long updated past. `bun run setup:omp` installs the latest omp into `node_modules` without saving it (`OMP_VERSION=18.14.0 bun run setup:omp` for another one); typecheck and the suite need it, since tests drive the hook with omp's own `convertToLlm` (`tests/support/host.ts`), read sessions with omp's own parser (`tests/support/load-session.ts`), and `tests/omp-host.test.ts` runs keel inside a real omp session. omp needs a recent Bun (its `engines.bun`). Pi is not a dependency either: `bun run setup:pi` installs the latest Pi (`@earendil-works/pi-coding-agent`; `PI_VERSION=1.0.0 bun run setup:pi` for another one), and `tests/pi-host.test.ts` runs keel inside a real Pi session built with Pi's own SDK, `tests/pi-entry.test.ts` drives `pi.ts` with a fake Pi API, and `tests/context-edits.test.ts` checks the context-edit projection against Pi's own `buildSessionContext`; each skips where Pi is not installed. Install omp first, then Pi (`setup:omp`, `setup:pi`); each entry's typecheck reads both hosts' types. `bun run test` is `bun test --isolate`, each file in a fresh module registry: once omp is loaded in a process it answers Pi's package names with its own (its shim for Pi extensions on omp), so a Pi test after an omp test in one registry would test omp's copy. `tests/support/pi.ts` makes every Pi test check it has the real Pi (`assertRealPi`) and fail with that explanation otherwise; npm may also nest Pi's `pi-ai` under Pi's package, so resolve Pi's own dependencies from Pi's directory. `tests/golden.test.ts` builds one session in a real omp and a real Pi (`tests/support/golden-session.ts`: scripted reads, both hosts' edit shapes, failing then passing tests, commits, a pin, compactions by command and automatic, nine recall calls) and compares every summary, its details and the recall outputs byte for byte with `tests/fixtures/golden-<host>.json`; a change to what keel writes shows there, and is recorded again on purpose with `bun run tests/support/golden-session.ts omp > tests/fixtures/golden-omp.json` (and `pi`). `tests/pi-shapes.test.ts` runs Pi's message roles and `edit` shape through the hook on Pi's `convertToLlm`. CI runs everything against the latest of both hosts and against the floor of each peer range in `package.json`, on every push and pull request and weekly.

`bun run scripts/real-sessions.ts` compiles the largest real sessions on this machine (read from copies, with the host's own parser; `--host=pi` for Pi's): `report` (the default) prints their compression and recall numbers as JSON, `show` each session's entries beside its summary, and `save NAME` writes the summaries to `/tmp/keel-compare/NAME/` to diff two branches' output.

`tests/long-horizon.test.ts` holds the long-horizon floor: 60- and 120-turn sessions with planted facts, worked through by a real model in omp, or in Pi with `KEEL_LH_HOST=pi` (`tests/support/long-horizon.ts`; the session is opened by `tests/support/host-session.ts`, with the provider in omp's `models.yml` or Pi's `models.json`, and Pi's `/compact` standing in for omp's idle pass, which Pi does not have). Nothing stands in for omp or the model: the model is a real provider set up as a user sets one up (a `models.yml` provider whose key omp reads from the environment): DeepSeek V4.1 Flash (`deepseek/deepseek-v4.1-flash` on OpenScale, `https://api.openscale.so/v1`), run when `KEEL_LH_API_KEY` in the environment holds a key for it (`KEEL_LH_BASE_URL`, `KEEL_LH_MODEL` and `KEEL_LH_API` point it elsewhere); without it the tests are skipped, as they are in CI. The benchmark scripts also read it from `research/long-horizon.env` (git-ignored, `KEEL_LH_API_KEY=…` lines); the tests do not, so a plain `bun test` never starts hours of model turns. Each turn is a request telling the agent what to do (read a module, make an edit, run its tests, commit); the agent does it through omp's real tools on a real project in a real git repository with real `bun test` tests (each turn's pass once its edit is made; turn 25's fails on rounding until the agent fixes it). omp counts the context from the provider's usage, compacts on its threshold and in its idle pass every 6 turns, and commits each compaction; keel is loaded from this package, and recall runs through the session's `keel_recall` tool. The facts are found afterwards in the session by content and keel's `#N`. A run takes about an hour (300 model turns). omp builds child shells' env from the env it loaded with, so nothing the session runs may depend on a `PATH` set later. `bun run scripts/benchmark-long-horizon.ts` prints the per-fact table (`… 60 6 all` for a 32K, 128K and 1M window); run it before and after a change to the summary or recall.

`scripts/benchmark-cybench.ts` (`tests/support/cybench.ts`) runs [Cybench](https://arxiv.org/abs/2408.08926) (Apache-2.0) as one long session on the same model, in omp or, with `--host=pi`, in Pi (its logs then start `cybench-pi-`; both benchmark scripts take `--host`): its 17 file-only capture-the-flag tasks (binaries to reverse, a pcap, emails, crypto) back to back in omp, answering each task's own subtask questions, then the same questions asked again tasks later, with keel, keel without `[Working Set]`, or the host's own compaction (`keel`, `keel-no-ws`, `own`; `omp`, `vcc` and `vcc-no-ws` are their old names). Its window argument may be `provider`: the window the provider lists for the model, as a user's catalog would hold it (`providerModel` in `tests/support/host-session.ts` reads the provider's `/models`, the benchmark's own call), and the prices are the provider's either way, so the cost the host records of each request, which the payback rule reads, is real; the result reports what keel learned of the model (`keel-models.json`) beside the chars per token the session's own record shows. It fetches Cybench at a pinned commit into `research/cybench` and sets each task up with the task's own `init_script.sh`, and the agent then inspects and runs the challenge binaries: it runs code from outside this repository, so run it in a sandbox or a throwaway container, never on a machine that matters. `.claude/settings.json` allows that one command (`bun run scripts/benchmark-cybench.ts …`) so an agent session can run it without a prompt; keep the key in `research/long-horizon.env` so the command stays that plain. It is a benchmark, not a test: nothing in `bun test` runs it.

omp's own docs ship inside its package (`dist/docs-index.generated.txt`: a JSON list of names, a newline, then a base64 gzip of the bodies); `extensions.md`, `compaction.md` and `session.md` cover what keel uses. Its sources are in `node_modules/@oh-my-pi/pi-coding-agent/src` (`session/messages.ts` for `convertToLlm`, `extensibility/shared-events.ts` for the events). Pi's docs are in `node_modules/@earendil-works/pi-coding-agent/docs` (`extensions.md`, `compaction.md`, `session-format.md`, `sdk.md`), its types in `dist/core/extensions/types.d.ts` and `dist/core/session-manager.d.ts`, and its code in `dist/` (`core/agent-session.js` for the compaction flow, `core/compaction/compaction.js` for `shouldCompact`, `core/session-manager.js` for the context projection).

## The Lisp core

`lisp/` is keel's core, in Common Lisp on SBCL: everything keel decides is decided there. The hosts load only JS/TS extensions, so `index.ts`, `pi.ts` and `src/` stay TypeScript, do what only the host can (its events, its session manager, its `convertToLlm`, `appendEntry`, listing a directory by modification time, which SBCL reads only to the second) and hand the rest to the core: one JSON object in, one out (`lisp/src/server.lisp`, which lists every op and its shape), from `src/core.ts` (`core()`, synchronous). The core answers a host's call or event with what to do as data, EFFECTS (`lisp/src/surface.lisp`: append an entry, tell the user, send a message), which `act` in `src/host.ts` carries out in order: the TypeScript side decides nothing, which is why CI's import check allows `node:child_process`. Where the system has named pipes, one core process stays up per host process (`--serve`, `lisp/src/live.lisp`): `core()` writes a request line to its pipe and reads the answer line with `writeSync`/`readSync`, and the core keeps the session files it read parsed (`jsonl-values`, which parses only the lines a file gained) and what is worked out of each value once (`derived` in `js.lisp`: an entry's rendering, the text search reads, its folded form); the values are shared, so nothing changes them in place. It ends when its host does or after 5 minutes idle, answers a request past 55 s as failed, and one that dies is replaced; on Windows, with `KEEL_CORE_LIVE=off`, or when it cannot start, each request runs its own process with `spawnSync` (`tests/live-core.test.ts`). The ops and where they live:

- The snapshot (`src/host.ts` `hostSnapshot`, read by `lisp/src/host.lisp`): every op for a host event carries one, the same shape for all: the host's profile, keel's config path, the session file, the cwd, the model and the context the host counted, the session's entry tree as a skeleton (a message its role, timestamp, attribution, a tool result's call id and omp's steering mark, which eviction ties a request's messages to `#N` by; a compaction where its kept tail starts; keel's pin and evict entries whole) and the branch as ids. From it the core counts `#N`, finds the branch, loads the settings, works out the window and records the host's policy; no caller reduces the session its own way.
- `compact` (`src/compaction.ts`), in two calls: the core decides whether the pass is keel's (the command's marker, the provider opt-out) and lists what the host's `convertToLlm` must convert (each live message on the branch as the context holds it, Pi's context edits applied once, and the original keel kept of what omp rewrote); the hook converts them (the one thing the core cannot do) and asks again; the core answers pass, cancel (with what to tell) or the compaction in the host's own result shape, with its outcome line; with `debug` on, the core writes a record of the pass beside the config (`keel-debug.json`). `host.lisp` reads the event; `compaction.lisp` holds what the summary makes of each conversion (roles left out, what is injected), the live window, the cut and its token-budget rescues, the running-turn and whole-window cuts, smart keep-tail, `[History Index]` (`history.lisp`), `[Task State]` (`task-state.lisp`), `[Working Set]` (`working-set.lisp`), both reading the calls, results, open failure and request through `calls.lisp`, the readers of an earlier compaction's details and state, the growth guard and the details stored, sized first by `window.lisp` (each host's trigger from the policy it hands the hook, a recovery's bound, the budgets, the context's overhead and chars per token).
- `summarize` (`tests/support/compile.ts` `compileSummary`, for tests and scripts): `blocks.lisp` (sanitize, host noise, normalize), `extract.lisp` (the sections), `brief.lisp` (the brief and its ranking), `summary.lisp` (render, the stored state and its merge, the legacy reader of an older summary's text).
- `surface`, `tool`, `command`, `session-start`, `message-end`, `context` (`src/register.ts`): `surface.lisp` defines the tools (their text and JSON Schema) and commands keel registers, written down in `src/surface.ts` (generated by `scripts/surface.ts`, held to the core by `tests/surface.test.ts`) because a host registers them at load, before a core may be built; each call through them and each of those events comes back as text and effects. Recall, for `keel_recall` and `/keel-recall` alike: `request.lisp` (the tool's params repaired, the command's text parsed, the `Ignored:` note), `session.lisp` (a session file's entries, `#N`, the active branch, a fork's parents, the kept originals), `render.lisp` (a message as recall shows it and search reads it, and the one reading of a tool call), `search.lisp` (BM25 with stems, a relative floor and a cap; regex queries), `sessions.lisp` (the project's other sessions) and `recall.lisp` (every action, both surfaces' hints, the cap).
- Turns out whole (op `context`, `keel_context`, `/keel-evict`): `evict.lisp`, old turns out of the context whole. A ledger of `keel.evict` custom entries replayed along the branch (`read-evictions`); turns are the live window cut at each request the user made, a steer (omp's `steering` mark) staying in the turn it steers (`branch-turns`); `context` gets the host's next request, ties each message to its `#N` by role, timestamp and call id (the snapshot's skeleton carries them), drops the turns that are out, puts one line in their place and the pinned notes in one block first (with `keel_context` there or anything out; `notes-block`), and past `+evict-at-share+` of the trigger records the oldest finished turns as out (the estimate: the provider's count for the last request less what was sent then, plus what is kept now); `evict` is `keel_context` and the evict command, sizing turns from the session file. `mirror.lisp`: the context as a file the agent edits (Context Language Models): with `keel_context` there, each request is written beside the session (`.keel-context.md`, and `.keel-context.last` as written), one block per turn under a `[[CTX_…]]` line; before the next request the agent's edit is read back as ledger ops (a deleted turn evicted, a rewritten one evicted with its `text`, which stands in its place, text between blocks an `insert` after the turn before; the running turn left as it is).
- `settled`, `outcome`, `settings`, `args`, `raw-capture`, `placeholders` (and `window`, `limits` for tests), and what `tool`, `command`, `session-start` and `message-end` run: `window.lisp` (an overflow error's limit, the trigger a settled run checks), `limits.lisp` (`keel-models.json` learned into and read: a stated limit, the largest prompt accepted, which outgrows a wrong one, and the model's chars per token, which eviction reads through `*chars-per-token*`; whether a settled run compacts in the host's stead), `outcome.lisp` (the outcome line, what `/keel` says when nothing was compacted, whose details a compaction carries, the provider opt-out), `settings.lisp` (the config file read and scaffolded, written as `JSON.stringify(value, null, 2)` writes it), `pins.lisp` (a `keel_pin` call or pin command, a named note defined again replacing the one it named, the user's notes left as they are by the agent, and a session starting carrying the user's named notes of the project's last session; the ops it decides come back as effects), `args.lisp` (`/keel`'s text and the customInstructions the hook gets back), `raw-capture.lisp` (what omp may rewrite, kept in `<session>.jsonl.keel-raw`, and the pointer on omp's placeholders). What a binding has seen and kept stays its own state, in TypeScript.
- For tests: `cut`, `working-set`, `request`, `load`, `search`, `regex` run one part alone, as do `args` on `instructions` and `outcome` on `stats`, `details` and `settings` (the compaction reads them inside op `compact`). The test preload builds the core as keel does (`buildCoreNow`, `src/core.ts`). The lint's dead-function check counts only `lisp/src` and `build.lisp`: a function only the Lisp tests call is dead.

The core is the executable `KEEL_CORE` names, or else the build of this copy's `lisp/` sources, `lisp/build/keel-core-<hash of the sources>` (`KEEL_CORE_BUILD_DIR` puts it elsewhere), which `src/core.ts` builds itself with the user's `sbcl` (or `SBCL`) the first time it is needed: in the background, a few seconds, a lock keeping two sessions from building at once, and again after an update. Until it is there (being built, no SBCL, a failed build) `core()` throws `CoreUnavailable`, whose message is what the user is told, and every surface catches it (`whenCore` in `src/core.ts`): the compaction hook leaves the pass to the host and tells once per binding, the tools and commands answer with the reason, raw capture tries again on the next event, the config's scaffold on its next load (`tests/core-wait.test.ts`). A core that fails throws. `sbcl --non-interactive --load lisp/build.lisp` dumps it to `lisp/build/keel-core` (`KEEL_CORE_OUT` for another path; git-ignored; ~40 MB, links only libc and libm, starts in ~5 ms).

It has no dependencies but SBCL: JSON (`lisp/src/json.lisp`: false, null and `[]` read as `:false`, `:null` and `#()`, never `NIL`; numbers read as `JSON.parse` reads them and written as `String()` writes them) and the test runner (`lisp/test/support.lisp`) are its own, and session text is never given to the Lisp reader (`read` interns into any package a `pkg::` names). It was ported from TypeScript and keeps JavaScript's arithmetic: lengths, cuts and offsets in UTF-16 code units (`js-string.lisp`), doubles where JavaScript had them, words counted by SBCL's UAX #29 segmentation (as Intl.Segmenter, except that each ideograph of a dictionary-segmented script is a word). Regex queries and terms run in `regex.lisp`, JavaScript's non-unicode `/i` dialect: its syntax errors (on which a search reads the query as text), UTF-16 code units, case folding by the spec's Canonicalize, named groups (by the spec's ID_Start and ID_Continue, as V8 reads them), Annex B's legacy escapes, and a 3 s budget; only a back-reference into or inside a look-behind, which JavaScript matches backwards, is refused, and such a query is searched as text.

Tests: the preload (`bunfig.toml`, `tests/support/core-on.ts`) builds the core and every test runs on it. The summary's and the plan's tests drive `compileSummary` and the hook (`tests/support/summary.ts`, `tests/support/host.ts`); recall's call `keel_recall` on session files written from their messages (`tests/support/pairs.ts`); the window rules come from op `window` (`tests/support/window.ts`), and `tests/window.test.ts` holds each host's trigger to the host's own function. `tests/lisp-regex.test.ts` compares compile errors, `test`, `search` and match counts with JavaScript's own over 1,500 generated and 120 hand-picked patterns. The host tests run all of it in a real omp and a real Pi. The Lisp tests (`lisp/test/`: stems, the recall cap, the token estimate, read selectors, JSON, strings): `sbcl --non-interactive --eval '(require :asdf)' --eval '(push (truename "lisp/") asdf:*central-registry*)' --eval '(asdf:test-system "keel-core")'`.

## Layout

The TypeScript is the binding alone, eight files:

- `index.ts` (`omp.extensions` in `package.json`): `register(pi, ompHost(pi))`.
- `pi.ts` (`pi.extensions`): `register` on Pi's host, with `convertToLlm` and `getAgentDir` imported from Pi's own package (Pi's loader resolves it to the running Pi) and Pi's trigger from its `session_before_compact` (`reason`, `willRetry`).
- `src/host.ts`: what differs between the hosts (`HostProfile`: name, which is also the trigger rule the core applies, the old command prefix kept as an alias, settle event, models file, whether it rewrites messages in place; `OMP_HOST`, `PI_HOST`) and the host's functions (`convertToLlm`, `agentDir`, `triggerOf`); omp's host (`ompHost`: its functions from `pi.pi`, the trigger from `auto_compaction_start`, since omp's `session_before_compact` carries none); what only the host can read (`hostSnapshot`, `hostBranch`/`hostEntries`, `projectFiles`: the project's other session files newest first); and acting on the core's answers (`act`, `tell`, which owns "the UI may be gone", `tellLater`, `deliver`, `compactAndWait`, `registerCommand` with its old-name alias).
- `src/register.ts`: everything keel registers, the same on both hosts: the tools and commands of `src/surface.ts`, each call handed to the core with the snapshot and its answer acted on; `session_start`, `message_end` and `context` likewise.
- `src/compaction.ts`: the one flow whose state the binding keeps, since the host runs it across events and calls: `session_before_compact` (the core's two calls, the host's `convertToLlm` between them), `session_compact` (the outcome told once the host applied keel's compaction: `state.written`, matched by its summary), `/keel` (asks the host for a pass and waits), and the pass keel starts once a run settles past its own trigger (omp's `agent_end`, Pi's `agent_settled`).
- `src/raw-capture.ts`: on omp, copies the originals of what omp may rewrite as they land, into `<session>.jsonl.keel-raw` (the core writes and reads it), and points omp's placeholders at them; which entries it has seen and kept is the binding's state.
- `src/core.ts`: the core process (live or one per request), its build, `CoreUnavailable` and `whenCore`. `src/settings.ts`: where the config file is (the core reads and scaffolds it).
- `src/surface.ts`: generated, see above. Each binding keeps its own state (`register` builds it), never a module variable.
- The one reading of a tool call (its kind, the files it works on, the command it runs, what it is about, the text it writes), by the names and arguments of omp's and Pi's own tools and by shape for another extension's, is the core's (`lisp/src/render.lisp`); nothing else matches a tool name or argument.
- The summary (op `summarize` alone, `tests/support/compile.ts`, with the shapes it stores) is the core's: `lisp/src/blocks.lisp` → `extract.lisp` (this window's sections) → `summary.lisp` (merged into the state the previous compaction stored in `details.summaryState`; rendered, the only place summary text is written; a previous summary with no stored state read from its text, in a frozen copy of the format it was written in, the only place summary text is read) with `brief.lisp`; `[History Index]` (stored in `details.historyIndex`), `[Working Set]` (`working-set.lisp`: from the originals of what is summarized and what is kept, its `#N` in `details.workingSet`) and `[Task State]` (`task-state.lisp`: the latest request, the calls since, their failures, changes and the open failure; built again at every compaction, never carried) are built in the plan, `compaction.lisp`. The session file as both hosts write it (what `#N` counts, `index-by-id`; the header and the parent session; omp's `/clear` boundary) is read by the core (`lisp/src/session.lisp`).
- Tests drive keel through `tests/support/binding.ts`: `fakeHost()` runs the real `register()` on a fake host API that records what keel registers, appends, tells and sends; `callTool`, `callCommand` and `requestContext` call the core as `src/register.ts` does, synchronously.
- `media/readme/`: the README's animation (`evict.gif`) and its source, a [raea](https://raea.io) composition (`evict.tsx`); its `README.md` says how to render it again.

## Rules

- The code is the API: what keel relies on of a host comes from that host's own source, types and docs in its package, never a guess or another host's. omp and Pi share a lineage, so the shared modules are typed against omp's API and `pi.ts` hands them Pi's binding; where the hosts differ (trigger rule, trigger source, settle event, commands, what rewrites in place), the difference goes through `src/host.ts` (the profile and the host's functions), not a branch on the host's name in shared code.
- Support each whole peer range (omp `>=18.14.0`, Pi `>=1.0.0`; CI tests both floors and the latest of each). Raise a floor in `package.json` when a change needs a newer host; otherwise use a newer API only behind a check that keeps older releases on the old path.
- Nothing under `src/` or `index.ts` imports a package at runtime, omp's and Pi's included: types come from `@oh-my-pi/*` and `@earendil-works/*` with `import type`, omp's functions from `pi.pi`, and what a host's docs describe is ported into the core (as omp's and Pi's triggers and Pi's context edits are, `lisp/src/window.lisp`, `context-edits.lisp`), not imported. `pi.ts` alone imports Pi's own package, as Pi's extension API has it (Pi's loader resolves it to the running Pi). CI checks that `bun build index.ts --target bun --packages external` imports nothing, statically or dynamically, but node builtins, and `pi.ts` nothing else but `@earendil-works/pi-coding-agent`.
- keel works with the host as configured: it never changes omp's or Pi's settings and never asks the user to. On Pi, every compaction asks the hook (`session_before_compact` with `reason` and `willRetry`), and the summary reads the branch as Pi's context holds it (its `context_edit` omissions and replacements applied), while recall reads the raw file; Pi never rewrites an entry, so nothing is kept aside. On omp: it never changes omp's settings (only omp's settings registry, a package import, can) and never asks the user to. Every omp method that writes a summary (`remote`, `snapcompact`, `handoff`, `soft`, the notes-backed rollover) asks the hook first, and the hook answers every automatic pass, recovery included (a running turn's newest steps kept, or the whole window summarized; cancelled with the reason only when no summary can shrink it), so none of them writes one. It steps aside only for the user's opt-outs (`overrideDefaultCompaction: false`, `skipForProviders`) and when nothing is live. omp's shake runs before it (an overflow, when shake is the first usable method) or after it (the post-commit rescue), and hands over through `soft`. What runs around it rewrites messages in place (shake, `supersedeReads`, `dropUseless`, the age-based prune), so keel keeps the originals as they land (`src/raw-capture.ts`, `lisp/src/raw-capture.lisp`, `keepOriginals`). Recall reads them for the entries omp rewrote (`prunedAt`, an `artifact://` splice), falling back along a fork's `parentSession` chain; the summary is written from them (the cut and budgets count what the context holds); and on omp's `context` event, omp's placeholder for a kept result gains ` (the original: keel_recall expand:[N])`, the same text on every request so the prompt cache keeps it. The copy comes from omp's entries, not the event's message, which omp de-obfuscates for display. `tests/omp-host.test.ts` checks it in a real omp session.
- omp binds the factory again for every subagent session while module state is shared (Pi binds it per session runtime), so per-session state lives in the binding `register` builds (its `Config` from the host's agent dir, `createCompactionState()`, raw capture's own), never in a module variable.
- `#N` refs in summaries are session-wide entry indices that `keel_recall` resolves. Any change to which entries are indexed must keep them stable; `[History Index]` ranges are `#N` too. Pins are `custom` entries, so they are never counted. In another session (`session:'id'`, `scope:'project'` hits) `#N` is that session's own.
- Sections carried across compactions are merged from the structured data the previous compaction stored (`details.summaryState`) or re-capped verbatim, never re-written and never parsed back from the summary text (only a summary with no stored state is, once, by the legacy reader in `lisp/src/summary.lisp`): rewriting a previous summary is how LLM compactors lose detail compaction after compaction. Keep the summary bounded as the session grows (the long-horizon test checks it). `[Working Set]` is not carried at all: it is chosen again at every compaction (the merge drops the previous one), within the budgets' `workingSetTokens` (`lisp/src/window.lisp` `compaction-budgets`) and at most half of what the compaction removes. It picks by paths, failure flags, recency and recall's own ranking, never by wording.
- Agents act on recall and summary text (headers, hint lines, `Ignored:` notes). Treat it as an interface: change it on purpose, and update the tests that pin it.
- keel was omp-vcc (and before that pi-vcc), and what was written under those names stays readable: `compactor: "omp-vcc"` and `"pi-vcc"` details (`+legacy-compactors+`), `omp-vcc.pin` and `omp-vcc.evict` entries and `omp-vcc-pin`/`omp-vcc-budget` notices (`pin-entry-type-p`, `evict-entry-type-p`, `notice-type-p` in `lisp/src/names.lisp`, the entry types whose data the snapshot carries in `src/surface.ts`), `<session>.jsonl.vcc-raw` (`raw-store-paths`), `omp-vcc-models.json` (read until `keel-models.json` is written), `omp-vcc-config.json` then `pi-vcc-config.json` (copied to `keel-config.json` once), and `OMP_VCC_*` env vars where the `KEEL_*` one is unset. The commands are `/keel…` on both hosts, each also registered under its old name (`/omp-vcc…` on omp, `/pi-vcc…` on Pi) by `registerCommand` in `src/host.ts`. Only what keel writes uses the new names.
- The smart keep-tail limit (25k) is keel's own and does not follow omp's `compaction.keepRecentTokens`; it, the summary budget, the summary's section sizes and the growth guard's margin scale with the trigger (`compaction-budgets` in `lisp/src/window.lisp`), and `expand`'s clips with the recall cap (`expand-detail-chars` in `recall.lisp`). All must stay the old numbers on a ~128K window. A new size limit that depends on how much context there is belongs there too, not in a constant.
- keel makes no network calls. The window is the host's (`ctx.model.contextWindow`, which omp's discovery fills from the provider, and Pi's catalog and `models.json`) or a smaller limit an overflow error stated; keel does not ask providers itself.
- Tests that read settings set `KEEL_CONFIG_PATH` to a temp file, never the user's config. `tests/real-sessions.test.ts` runs for each host whose sessions exist here (`~/.omp/agent/sessions`, `~/.pi/agent/sessions`), reading them with that host's own parser.
- `research/` is git-ignored local data (real sessions, replays). Never commit it or quote session content in commits or PRs.
- Note user-facing changes in `CHANGELOG.md` under `[Unreleased]`.
